    Trad Roguelike Dev - Vision Systems

    One of the most distinctive elements of a traditional roguelike is the way the map only shows areas that the player can see. Most TradRLs use top-down tilemaps, but unlike other dungeoncrawlers and fantasy games with similar perspectives (arpgs for example) TradRLs use various techniques to simulate the effect of the world being viewed from the main characters location.

    Brogue

    In the image of Brogue above the areas of the map that are currently visible by the player (@) are drawn using a light palette, the areas that the player has seen but currently can't see are drawn in muted colors and the areas the player has never seen are simply not drawn at all (black).

    This approach makes exploring more dangerous, mysterious and immersive. But it also mimics the long term memory of the player by drawing out areas they have already visited. In this way the map builds up in the same way a players knowledge of the dungeon would. One key element of this 3 state solution is that monsters, items and active events (fires etc) are only shown in the currently visible zones. The remembered portion is usually limited to architecture alone.

    There are a number of different ways to calculate the players visible field of view on a tilemap grid. Adam Milazzo outlines some of the most common in this excellent article

    https://www.adammil.net/blog/v125_Roguelike_Vision_Algorithms.html

    There are different issues with any implementation, in my case I initially used a quadrant shadowcasting approach, but found that it wasn't symmetrical. I'll explain why that is important for me an my project in a minute.

    There are very few 3D TradRLs and so I had few examples to learn from. Jupter Hell is perhaps the most well known and does a great job of porting the visiblity approach to 3D.

    Jupiter Hell

    In the image above you the three types of tile state are easily seen; a visible corridor, a previously visible room to the top of the image, and currently unknown areas on the edges of the screen. This is done in an extension of the color palette treatment mentioned above for 2D versions.

    Usually the visibility of a tile is stored in an array. This could be part of the array that defined the tiles themselves, but more often its a separate array that hold just the visibility state of every tile on the map. This array can then be examined to work out the state of an individual tile and choose what colour palette to draw it with. In my game I also store this information in a texture map and then this texture is used in a series of shaders to tint the 3d tiles.

    Texture memory (white=in view, grey=known) and Top down view of the values applied

    In game view of the same location.

    One extra element to note is that the player actually has two separate visibility maps, one is the map for the current turn, showing only what the player can see right now. The other is a cumulative version of this map, the current turn map simply adds any newly seen tiles to the cumulative one. The final texture map is a combination of these two (white as current and grey as cumulative memory)

    Now in a tile based TradRL movement is often instant, with players moving a tile immediately and any visibility updating in the same frame. This is fine when the movement is purely step based. But in a 3D environment with character models, the charters have to walk (using animations) from one tile to the next. This movement can clash with an instant change of the visibility map.

    I followed what I think Jupiter Hell is doing here. My game holds 2 versions of the visibility texture map, the current turn version and the previous turn version. Whenever  a new map is calculated my game crossfades from the old to the new over a short period.

    single step version

    with crossfade

    But how are the visibility maps actually applied in 3D space? Initially I thought I might be able to place the visibility fog over the scene like some sort of filter. But of course this doesn't work because different camera angles mean that you would be looking through the plane of the visibility map like it was a slice of fog or something. The visibility map needs to effect every pixel in a vertical stack, regardless of camera position, so that whatever angle you are viewing the scene from at the colouring of a tile is the same.

    Bad fog approach

    I ended up achieving this effect by writing a series of custom shaders for all the 3D objects. These shaders take the two versions of the visibility map (current and previous) and then use the world position of each vertex to map the colour values. If you have ever used a tri-planar shader, this is basically the same approach but only on the planar axis.

    The two texture maps sent and used like triplanar maps

    I send some map co-ordinate scaling info and the current crossfade values in code using  global shader values. The actual colour tints for each part of the visible map can be tweaked, but I'm fairly happy with the results.

    Finally I decided to use the same field of view functions to provide the units in the game with their vision systems. Each character that can see (mostly enemies, but NPCs too) runs the same visibility calculation as the player. This results in a visibility map (hidden for all units except the player) which can be examined by the unit in order to tell if a particular tile is visible during that turn. Being able to see a tile also means you can see any characters on that tile. This system is plugged into the general ai of the unit , providing sensor data for combat behaviour etc.

    This is why I needed the visibility algorithm to be symmetrical, otherwise the player might be able to see an enemy and the enemy might be ignorant of the player, even though the onscreen visibility suggests otherwise. I ended up using a "diamond walls" version of code that was symmetrical and so far its performing well.

    There are of course loads of other tweaks that can be made to the systems described here, and the requirements of different roguelikes require different styles of vision algorithm, but I'm pleased I managed to get one of the most iconic elements of TradRL gameplay translated into 3D.
